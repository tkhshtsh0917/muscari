# 設計

[English](../design.md)

muscariが何を計算するのか、なぜこの作りにしたのか、元にした研究とどこが違うのか、何を検証済みで何が未検証なのかを説明します。使い方は[README](../../README.ja.md)にあります。

## 対象範囲

SAE型の学習型疎検索は、SPLADE型モデルの語彙をスパースオートエンコーダの潜在に置き換えます。学習は二段階です。まずバックボーンの隠れ状態を再構成するSAEを学習し、次にその上で検索モデルを学習します。muscariはエンコーダをバックボーンとする場合の第一段階を実装し、評価済みのSAEを書き出すところまでを扱います。

## パイプライン

```text
行 -> (プレフィックス, テキスト) -> 凍結したエンコーダ -> 本文トークンの活性
   -> シャッフルバッファ -> トレーナー (topk | saelens) -> sae.safetensors + sae_config.json
   -> ホールドアウト評価
```

### 1. テキストストリーム（`muscari.data`）

行はマッピングです。指定した列ごとに、エンコーダが期待するプレフィックスを組み合わせます。セルは一つのテキストでも、テキストのリストでもかまいません。1行に複数のハードネガティブを持つデータセットをそのまま読めます。

- **重複の除去。** 検索用データセットでは、同じ文書が多くのクエリのネガティブとして繰り返し現れます。`(プレフィックス, テキスト)`が完全に一致するものは2回目以降を捨て、頻出するネガティブに重みが偏らないようにします。異なるテキスト1件につき64ビットのハッシュを一つメモリに保持します。
- **内容によるホールドアウト。** テキスト自身のハッシュが指定した割合を下回るとき、そのテキストをホールドアウトに回します。行や列には依存しないので、同じ文書が学習側と評価側の両方に現れることはありません。行単位で分割すると、共有されたネガティブが評価側に漏れます。
- **エポック。** データを読み切ると先頭から読み直します。重複の除去もやり直します。

### 2. 活性（`muscari.activations`）

SAEは`last_hidden_state`で学習します。Sentence Transformersが`token_embeddings`として公開しているテンソルです。ModernBERTでは最終のLayerNormを通した後の出力にあたります。`--layer`を指定すると`hidden_states`の要素を使います。

次の条件をすべて満たす位置だけを残します。

1. パディングではない（`attention_mask`）。
2. 特殊トークンではない（`special_tokens_mask`）。
3. 文字範囲の終端がプレフィックスの内側にない（`offset_mapping`）。`--keep-prefix-tokens`を指定した場合、この条件は使いません。

プレフィックスの終端をまたぐトークンは本文を含むので残します。文字オフセットを返さないトークナイザでは、プレフィックスだけをトークン化したときのトークン数`n`を求め、先頭から`n`個の本文トークンを捨てます。プレフィックスのトークン化が後続のテキストの有無で変わらない場合、この方法は正確です。

テキストは16バッチ分ごとにまとめ、その中で長さ順に並べてパディングを減らします。エンコーダをautocastで動かした場合も、活性はfloat32で返します。

### 3. シャッフルバッファ

一つのテキストのトークン同士は強く相関します。長さ順の並べ替えは、隣り合うテキストの間にも相関を加えます。そこで活性を`--buffer-tokens`行のバッファに通します。バッファが満杯になるたびに、ランダムに選んだ半分をちょうど`--batch-tokens`行のバッチとして出力します。残りの半分は次に入ってくる活性と混ぜます。各活性が出力されるのは多くても1回で、捨てるのは最後の端数バッチだけです。バッファは学習デバイス上に一度だけ確保します。ピーク時のメモリはバッファの約1.5倍です。

### 4. SAE（`muscari.sae`）

```text
z     = TopK_k(ReLU(W_enc (x - b_dec) + b_enc))
x_hat = W_dec z + b_dec
```

- **初期化。** デコーダの各行はランダムな単位ベクトルで、エンコーダはデコーダの転置から始めます。その後、ランダムな単位ノルムの入力が平均して単位ノルムで再構成されるよう、エンコーダ全体を一つの係数でスケールします。`b_dec`は最初のバッチの幾何中央値から始めます（最大32,768行にWeiszfeld法を適用します）。
- **単位ノルムのデコーダ。** ステップのたびにデコーダの各行を正規化し直します。ステップの前には、各行に平行な勾配成分を取り除きます。
- **損失。** 再構成誤差を、バッチ平均を予測したときの二乗誤差で割ります。これはバッチにおける「説明できなかった分散の割合」（FVU）です。
- **死んだ潜在。** `--dead-after-tokens`トークンの間発火しなかった潜在を死んだものとみなします。発火とは、正の活性で選ばれることです。活性が0のまま選ばれた場合は発火に数えません。
- **AuxK。** 死んだ潜在のうち事前活性の大きい`aux_k`個が、生きている潜在の残差`x - x_hat`をデコーダのバイアスなしで再構成します。残差は勾配から切り離すので、この項が学習させるのは死んだ潜在だけです。値は残差の分散で割り、有限でなければ0にして、重み`aux_coef`で加えます。

### 5. 疎な逆伝播

あるトークンの損失が依存するのは、`k`個の事前活性（補助項ではさらに`aux_k`個）だけです。それ以外の事前活性に対する勾配は厳密に0です。それでも通常の自動微分は`(バッチ, 潜在数)`の密な勾配を作り、エンコーダの重みと入力のそれぞれに掛けます。順伝播と同じ大きさの積が2回余分にかかります。

muscariは、エンコーダとデコーダを、選ばれた要素だけをたどるautograd関数として実装しています。選ばれた事前活性に対する勾配を`g[b, m]`とすると次のようになります。

```text
grad b_enc[m] = sum_b g[b, m]
grad W_enc[m] = sum_b g[b, m] (x[b] - b_dec)
grad b_dec    = -sum_m grad b_enc[m] W_enc[m]      （エンコーダ側の寄与）
grad W_dec[m] = sum_b z[b, m] r[b]                  （r = d loss / d x_hat）
grad z[b, m]  = <r[b], W_dec[m]>
```

これらを行のチャンクごとにgatherと`index_add_`で積算するので、`(バッチ, n, d_in)`のブロックを逆伝播のために保持することはありません。テストでは、損失と勾配を、通常の自動微分による密な実装と、倍精度の数値微分の両方と比較しています。

補助項はトークンあたり最大256個の潜在を選びます。主項の16倍です。また、gatherがデータを運ぶ速度は、行列積が掛け算をこなす速度よりずっと遅くなります。そこで補助項の経路は、死んだ潜在の列に限った密な行列積を優先します。CUDAでは常にこの方法を使います。それ以外のデバイスでは、死んだ潜在の数が`64 * aux_k`以下の間だけ使い、それを超えるとgatherを使います。gatherの時間とメモリは死んだ潜在の数に依存しません。どちらの経路も同じオラクルでテストしています。

`benchmarks/sae_step.py`による測定結果です（潜在65,536個、幅768、`k = 16`、`aux_k = 256`、ランダムな活性、x86_64のCPUで2スレッド、PyTorch 2.15、最初の1ステップを除く3ステップの中央値）。

### 6. トレーナー

**`topk`**は、バッチごとに次の1ステップを実行します。

1. 学習率を設定します。全ステップの最初の`warmup_frac`で線形にウォームアップし、その後は0までコサイン減衰します。
2. ステップ前の時点の「死んだ潜在」のマスクで損失を計算します。
3. 逆伝播し、デコーダの平行な勾配成分を除き、Adamで更新し、デコーダを正規化し直します。
4. 潜在ごとの「最後に発火してからのトークン数」を更新します。

チェックポイントには、SAE、オプティマイザの状態、死んだ潜在の数え上げ、ステップ数とトークン数、設定、符号化済みのテキスト数が入ります。再開するとこれらをすべて復元します。途中で中断した学習に同じバッチを与えると、最後のパラメータがビット単位で一致することをテストで確認しています。コマンドラインから再開する場合、バッチは同じにはなりません。テキストストリームは符号化済みのテキストの続きから再開し、バッファは新しいシードでシャッフルし直します。そのため、中断時にバッファに残っていた活性は使われません。潜在数、`k`、バッチサイズはチェックポイントと一致している必要があります。学習の長さは延ばせます。

**`saelens`**は、SAELensの`TrainingSAE`（`topk`または`batchtopk`）を作り、同じバッチで`SAETrainer.fit()`を実行します。

| muscari | SAELens |
| --- | --- |
| `num_latents`、`k` | `d_sae`、`k` |
| `total_tokens`、`batch_tokens` | `total_training_samples`、`train_batch_size_samples` |
| `warmup_frac` | `lr_warm_up_steps` |
| `lr`、`lr / 100` | `lr`、`lr_end`（`lr_scheduler_name="cosineannealing"`） |
| `dead_after_tokens / batch_tokens` | `dead_feature_window`（ステップ数） |
| `aux_loss_coefficient` | `aux_loss_coefficient` |

SAELens 6.56の内部で固定されており、`topk`と異なる点は次のとおりです。補助損失は死んだ潜在を`d_in // 2`個使い、残差の分散で割らず、死んだ潜在が少ないときは値を小さくします。`batchtopk`はバッチ全体で大きい順に`k * バッチ`個の活性を残し、潜在ごとのしきい値を持つJumpReLU型のSAEとして保存されます。発火する潜在の数はトークンによって変わります。活性の正規化は、書き出す重みに畳み込めないため無効にしています。

muscariが変えている点が一つあります。デコーダのバイアスを、`topk`トレーナーと同じく最初のバッチの幾何中央値から始めます。SAELens本来の初期値は0です。エンコーダの隠れ状態には、全トークンに共通する大きな成分が含まれることがあります。バイアスが0のままだと、Top-Kの選択がその成分に沿った少数の潜在に固定されます。回帰テストでは合成した活性でこの現象を再現しています。一つの潜在が全トークンで発火し、再構成は平均を予測するより悪くなります。`--zero-b-dec`を指定すると、SAELens本来の初期化に戻ります。

短い学習だけでこのバックエンドを評価することはできません。SAELensの既定のデコーダのスケールでは、学習の初期に大半の潜在が使われなくなり、補助損失が時間をかけてそれらを呼び戻します。これは合成した活性で観察したものです。[実際のエンコーダでの試走](#実際のエンコーダでの試走)の結果はこれと矛盾しませんが、この要因だけを切り分けたものではありません。

### 7. 書き出し形式（`muscari.export`）

`sae.safetensors`は`encoder.weight (M, d)`、`encoder.bias (M)`、`decoder.weight (d, M)`、`decoder.bias (d)`を含みます。JumpReLU型のSAEでは`threshold (M)`も含みます。

`b_dec`の引き算はエンコーダのバイアスに畳み込みます。

```text
W_enc (x - b_dec) + b_enc = W_enc x + (b_enc - W_enc b_dec)
```

検索のヘッドに必要なのは`encoder.weight`と`encoder.bias`だけです。SAELensは`W_enc`を`(d, M)`、`W_dec`を`(M, d)`で保存しています。変換では両方を転置し、`apply_b_dec_to_input`が有効ならバイアスを畳み込み、`threshold`があれば写します。デコーダのノルムは、SAELensの推論用の書き出しの時点で重みに畳み込まれています。変換後のSAEとSAELens自身の推論モデルが同じ特徴と再構成を返すことをテストで確認しています。

`sae_config.json`は`format_version`、サイズ、活性化の規則（`topk`または`jumprelu`）、来歴を記録します。ローカルのモデルやデータのパスはファイル名だけを記録するので、ディレクトリ構成を明かさずにSAEを共有できます。

### 8. 評価

評価は書き出したファイルに対して行い、どちらのトレーナーの出力にも同じコードを使います。

- `fvu`は、再構成の二乗誤差を、評価したトークンの平均活性まわりの分散で割った値です。`l0`はトークンあたりの発火した潜在の平均個数です。
- `never_fired_frac`、`rare_frac`、`dense_frac`、`median_frequency`、`max_frequency`は、辞書がどれだけ偏りなく使われているかを表します。平均的な潜在は、トークンの`l0 / num_latents`で発火します。`rare_frac`はその10分の1未満の潜在、`dense_frac`は全トークンの10%を超える潜在の割合です。
- `by_prefix`は、プレフィックスごとの`fvu`と`l0`、そのグループがトークンに占める比率です。クエリは短いのでトークンのごく一部にしかならず、全体の数値はほぼ文書の性質を表します。
- `train_unused_frac`は、学習の最後の1,000万トークン（学習がそれより短ければ全体）で一度も発火しなかった潜在の割合です。トレーナー自身の記録から求めるので、評価に使うトークン数に左右されません。

評価用のサンプルから求める頻度の指標は、サンプルの大きさに左右されます。トークンが少ないと、まれにしか発火しない潜在は発火する機会がありません。そのため既定値は潜在1個あたり32トークン、最低20万トークンにしています。潜在65,536個なら約200万トークンです。

FVUが良くても検索が良いとは限りません。多くのトークンで発火する潜在は、転置インデックスの中でストップワードのように振る舞い、ポスティングリストを長くします。頻度の指標をFVUと並べて出力するのはこのためです。

#### プーリング後（`muscari.analysis`）

SAEを語彙にしたインデックスは、テキスト1件につきベクトルを1つ持ちます。各潜在について本文トークン方向の最大値を取ったもので、通常は先に`log1p`をかけます。インデックスの大きさは文書1件の非ゼロ次元数で決まり、検索の遅延はクエリ1件の非ゼロ次元数と、それが当たるポスティングリストの長さで決まります。そこで`evaluate_texts`はテキストの境界を保ったまま、プーリング後にどの次元が非ゼロになるかを測ります。潜在は、テキストの中の1トークンでも発火していれば、そのテキストで活性があると数えます。`log1p`のような単調増加の変換を値にかけても、非ゼロの位置は変わりません。

- テキストあたりの`l0`と、その中央値、95パーセンタイル。プレフィックスごとに出力します。トークンあたり`k`個の潜在が発火するので、`n`トークンのテキストで活性のある潜在は`k`個から`min(k * n, num_latents)`個の間になります。この範囲のどこに来るかで、1つのテキストのトークンどうしがどれだけ潜在を共有しているかが分かります。
- `max_document_frequency`と`dense_frac`は、多くのテキストで活性のある潜在を数えます。こうした潜在のポスティングリストはコレクション全体と同じ長さになり、何に反応していようと文書を区別する役には立ちません。
- `flops`は`sum_j p_a(j) * p_b(j)`です。`p_a(j)`は、プレフィックス`a`のテキストのうち潜在`j`に活性があるものの割合です。クエリのプレフィックスと文書のプレフィックスの組では、クエリ1件が触れるポスティングリストの要素数の期待値を、文書数で割った値になります。PariaらのFLOPS正則化が上から抑える量であり、naver/spladeが評価時に出力する値です。

いずれも、検索の学習をする前のSAEについての測定です。検索の学習はエンコーダを変えるので、これらの値は出発点であり、最終的なインデックスの予測ではありません。

#### 潜在ごと

`latent_statistics`と、コマンドラインの`inspect-sae`は、すべての潜在を一覧にします。潜在は、意味ではなく次の3つのどれかに反応していることがあり、それを見分ける数値を付けます。

- トークン：`top_tokens`の`share`と`token_rate`。発火のほぼすべてが1つのトークンで起き、そのトークンが現れるたびにほぼ必ず発火する潜在は、語彙の1項目と同じです。
- テキストの種類：`frequency_by_prefix`。クエリで発火し、文書ではほとんど発火しない潜在は、内容ではなくプレフィックスを表しています。
- 位置：`first_token_share`、`last_token_share`、`mean_position`。`1 / tokens_per_text`と比べて読みます。トークンが何であっても先頭か末尾で発火する潜在は、位置に反応しています。

`text_frequency`は、`frequency`をテキスト単位にしたものです。どのテキストでも数トークンだけ発火する潜在は、`frequency`が低く`text_frequency`が1に近くなります。インデックスに効くのは後者だけです。

## Gaoらとの違い

論文はarXiv v1のHTML版（2.1〜2.4節、付録AとB）を読みました。[参照実装](https://github.com/openai/sparse_autoencoder/tree/4965b941e9eb590b00b253a2c406db1e1b193942)は`sparse_autoencoder/train.py`を読みました。

| 観点 | Gaoら | `topk`トレーナー |
| --- | --- | --- |
| 入力の前処理 | 次元方向の平均を引き、各活性を単位ノルムにする | なし。検索時にSAEが生の隠れ状態で動く必要があるため |
| 学習率 | 一定 | 5%のウォームアップとコサイン減衰（ShizukuのSAEのモデルカード） |
| 重みの平均化 | EMA、0.999 | なし |
| Adamのepsilon | 6.25e-10 | PyTorchの既定値1e-8。変更できます |
| `aux_k` | 通常512。幅の半分に近い2のべき乗 | 256（モデルカード。参照実装の既定値でもあります） |
| `aux_coef` | 1/32 | 1/32 |
| 死んだ潜在のしきい値 | 1,000万トークン | 1,000万トークン |
| 死んだ潜在の数え方（参照実装） | ステップ単位。事前活性が1e-3を超えたら発火 | トークン単位。活性が0を超えたら発火 |
| 主損失のスケール（参照実装） | MSEに、サンプルから求めた固定の分散の逆数を掛ける | MSEをバッチごとの分散で割る |
| 初期化時のエンコーダのスケール調整 | 行う。論文のアブレーションは「効果なし、または弱い負の効果」と報告 | 行う |
| バッチサイズ | 131,072トークン | 8,192トークン（モデルカード） |
| 規模の拡大 | 専用カーネルで複数GPUに分割 | 1デバイス |

### ShizukuのSAEのカードの設定で実行する

Shizukuが使うSAEの[モデルカード](https://huggingface.co/mahiyama/modernbert-ja-310m-sae)には次のことが書かれています。`topk`トレーナーの既定値は、このすべてと一致します。

- 凍結した`sbintuitions/modernbert-ja-310m`の最終層の`last_hidden_state`
- 潜在65,536個、`k = 16`のTop-K、256個・係数1/32のAuxK
- Adam（ベータは0.9と0.999）、学習率5e-4、最初の5%でウォームアップしてコサイン減衰
- 8,192トークンのバッチ、最大長1,024、学習トークン数10億
- クエリと文書の重複除去、5%のホールドアウト
- 保存ファイルのテンソル名、形状、デコーダのバイアスの畳み込み

```bash
muscari train-sae \
  --trainer topk \
  --model sbintuitions/modernbert-ja-310m \
  --data-files corpus.jsonl \
  --columns query document \
  --out runs/modernbert-ja-310m-sae
```

カードに書かれていて、このコマンドに含まれないものが三つあります。

- **データ。** カードによると約8.46億トークン（文書70.1%、クエリ14.9%、Wikipediaの記事14.9%）で、mqa-ja、auto-wiki-qa、日本語Wikipedia、mmarco-jaなどから集めています。非公開のデータも含まれ、一部の評価セットと重なる項目は除かれています。muscariにこのコーパスを作る手順はありません。
- **モデルのリビジョン。** カードはリビジョン`77675fc`を挙げています。`--revision`には完全なコミットハッシュを渡してください。
- **評価。** カードは、ホールドアウトの文書200万トークンでのFVU 0.155、MLM損失の回復率0.944、学習の最後の1,000万トークンで未使用の特徴0%を報告しています。muscariは1番目と3番目を独自の形で出力します。MLM損失の回復率は出力しません。

カードに書かれていないこと（初期化、死んだ潜在のしきい値、シャッフル、損失の正規化、入力の正規化、学習に使ったライブラリ）はmuscari独自の選択で、多くはGaoらに従っています。したがって、得られるのは公開された設定での学習であり、あのSAEの再現ではありません。保存されるテンソルの配置はカードのファイルと同じですが、相互に読み込めるかは試していません。

## 実際のエンコーダでの試走

MPSを使うApple M5 Proで、短い学習を3回実行しました。実際のモデル、トークナイザ、データセットでパイプラインが動くことを確かめるためのものです。SAEの品質を示すものではありません。トークン数は本来の設定（10億）の0.5%で、シードは一つ、比較できる基準値もありません。

| 設定 | 値 |
| --- | --- |
| エンコーダ | `cl-nagoya/ruri-v3-30m`、`last_hidden_state`、幅256 |
| データ | `cl-nagoya/ruri-v3-dataset-ft`の`jsquad`。列`anc`に`検索クエリ: `、列`pos`と`neg`に`検索文書: ` |
| SAE | 潜在8,192個、`k = 16` |
| 学習量 | 500万トークン（8,192トークンで610ステップ）。100万トークン発火しなければ死んだとみなす。テキストの5%をホールドアウト |
| シード | 0（当時の既定値） |

| | `topk` | `saelens` `topk`、バイアスは0から | `saelens` `topk`、バイアスは幾何中央値から |
| --- | ---: | ---: | ---: |
| ホールドアウト20万トークンでのFVU | 0.441 | 0.511 | 0.467 |
| トークンあたりの発火した潜在 | 16 | 16 | 16 |
| 一度も発火しなかった潜在 | 0% | 91.5% | 54.1% |
| トークンの10%超で発火した潜在 | 0% | 0.4% | 0% |
| 一つの潜在の最大の発火率 | 6.3% | 23.7% | 7.4% |
| 所要時間（評価を含む） | 200秒 | 189秒 | 193秒 |

1回目の時間には、モデルとデータセットのダウンロードが含まれます。学習に使っていない`jaquad`の20万トークンで評価すると、`topk`のSAEはFVUが0.447で、一度も発火しない潜在はなく、10%を超えた潜在は一つ（10.1%）でした。どの学習でも31,616件の異なるテキスト、552万個の本文トークンを符号化しました。`topk`の学習の速度は、エンコーダ込みで毎秒約42,000トークンです。

「動いた」こと以外にわかったことは次のとおりです。

- **プレフィックスの規則は、このトークナイザで意図どおりに働きます。** 高速トークナイザです。`検索クエリ: `は`検索`、`クエリ`、`:`、`▁`の4トークンになります。どれも終端がプレフィックスの内側にあるので捨てられ、本文のトークンはすべて残ります。プレフィックスあり・なしの3つのテキストで、手作業で確認しました。
- **この隠れ状態には、大きな共通成分があります。** 10万個の活性で測ると、平均活性のノルムは35.0でした。各活性と平均との距離の平均（35.3）と同じ大きさです。二乗ノルムの半分を平均が占めています。
- **SAELensバックエンドでは、デコーダのバイアスの初期値が効きます。** 0の代わりに幾何中央値から始めると、一度も発火しない潜在は91.5%から54.1%に、FVUは0.511から0.467に下がりました。

わからないことは次のとおりです。

- `topk`の学習ログでは、記録したすべてのステップで死んだ潜在が0、補助損失も0でした。そのため、AuxKは実際の活性では動いていません。
- SAELens側で、なお半分の潜在が発火しなかった理由。上のSAELensバックエンドの説明のとおり、学習の短さが候補ですが、長い学習は実行していません。
- トレーナー同士の同条件での比較。各列は、補助損失、死んだ潜在の数え方、デコーダのスケール、初期化が異なります。

### 学習の長さ

同じ設定で、データセットの検索系9サブセット（`auto-wiki-qa-nemotron`、`jaquad`、`jqara`、`jsquad`、`miracl`、`mkqa`、`mr-tydi`、`quiz-no-mori`、`quiz-works`）を使いました。シードは42で、長さとトレーナーの組み合わせごとに独立に学習し、ホールドアウトの20万トークンで評価しています。SAELens側は、デコーダのバイアスを幾何中央値から始めています。

| 学習トークン数 | `topk`のFVU | `saelens`のFVU | `saelens`で一度も発火しなかった潜在 | 最大の発火率（`topk`／`saelens`） |
| ---: | ---: | ---: | ---: | ---: |
| 500万 | 0.444 | 0.474 | 54.1% | 5.3%／6.4% |
| 1,000万 | 0.396 | 0.420 | 17.1% | 6.6%／5.2% |
| 2,000万 | 0.360 | 0.365 | 0.9% | 6.6%／13.3% |
| 3,000万 | 0.341 | 0.342 | 0.8% | 14.2%／14.1% |

- SAELensバックエンドで使われなかった潜在は、学習の長さの問題でした。十分なトークン数があれば、二つのトレーナーは同じFVUに達します。短い学習では`topk`トレーナーが先行し、どの長さでもすべての潜在が発火しました。
- FVUは3,000万トークンでもまだ下がっています。長さを倍にするたびに、下がり幅は小さくなっています。
- `topk`の学習では、死んだと判定された潜在が一度も出ませんでした。この規模（幅256、潜在8,192個）では、AuxKは動いていません。
- 長い学習では、どちらのトレーナーでも、トークンの約14%で発火する潜在が一つ現れました。何に反応しているかは調べていません。
- 4回目の学習から、速度が毎秒約43,000トークンから約23,000トークンに半減しました。別々のプロセスにまたがって続いています。原因は切り分けていません。これらの学習では、エンコーダとSAEの時間を分けて記録していませんでした。

### CUDA

上の`jsquad`での500万トークンの学習を、NVIDIA L4でシード0のまま実行しました。FVUはfloat32で0.4406、エンコーダとSAEの両方にbfloat16のautocastを使うと0.4405でした。MPSでは0.441です。速度はそれぞれ毎秒約55,000トークンと約76,000トークンでした。

本来の幅（`cl-nagoya/ruri-v3-310m`、潜在65,536個）で300万トークンだけbfloat16で学習すると、L4での速度はエンコーダ込みで毎秒約15,000トークンでした。SAEの更新だけなら8,192トークンあたり133ミリ秒、毎秒約62,000トークンなので、時間の大半はエンコーダです。この速度なら、10億トークンにL4で約19時間かかります。これは300万トークンの学習からの外挿で、測定ではありません。

## 検証済みのこと

- 疎な逆伝播の損失と勾配：密な自動微分、および数値微分と比較しています。
- チェックポイントからの再開：同じバッチを与えるとビット単位で一致します。
- 書き出し：学習したモジュールと同じ出力を返します。`topk`と`batchtopk`では、SAELens自身の推論モデルとも一致します。
- 本文トークンの選択：手作業の順伝播と比較しています。高速トークナイザと、オフセットを返さないトークナイザの両方で確認しています。
- ホールドアウトの分割：互いに素で、決定的で、プレフィックスや行に依存しません。
- Apple MPSとCUDA：損失、勾配、活性がCPUと一致します。上の学習も最後まで動きました。CUDAでは、bfloat16のautocastの結果がfloat32と小数第3位まで一致しました。
- ruri-v3のトークナイザでのプレフィックスの除外：3つのテキストで、手作業で確認しています。

上の学習を除き、いずれもランダムに初期化した2層のBERT、または合成した活性を使っています。実行した環境は[検証状況](../../README.ja.md#検証状況)を参照してください。
